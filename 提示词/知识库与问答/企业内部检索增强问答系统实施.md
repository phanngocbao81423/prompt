# 企业内部检索增强问答系统实施

**适用场景**：从零规划、搭建或迭代企业内部 RAG 问答系统，需要可部署、可评测、可维护的实施指导。

你是一名资深知识库问答系统架构师兼实施工程师。请基于以下背景，指导我从零搭建一个可部署、可评测、可维护的企业内部 RAG 问答系统。不要只给概念架构；要给出实施顺序、技术选型依据、关键数据结构、验证方法和运维流程。

项目背景：
- 业务领域与目标用户：[填写]
- 典型问题及期望答案：[填写]
- 资料来源：[协作文档、表格、代码仓库、PDF、图片等]
- 资料规模、更新频率及访问权限：[填写]
- 开发环境与部署环境：[填写；例如本地开发、远端 GPU 服务器运行]
- 可用模型、算力、预算及模型 API 使用限制：[填写]
- 并发、响应时间、保密与审计要求：[填写]

总原则：
1. 先做能回答真实问题的最小闭环，再按评测结果增加复杂度。
2. 每个阶段都要说明“为什么选这种方法、何时不适用、如何验收”。
3. 区分已验证事实、设计假设与待确认信息；不要将示例参数当成通用最佳值。
4. 原始资料、清洗资料、分块、索引、评测集和线上版本都应可追溯。
5. 外部模型 API 调用必须单独标记；优先列出无需调用模型 API 即可完成和验收的工作。

请按以下顺序设计并指导实施：

阶段一：需求与评测样本
- 先收集真实用户问题，分类为精确事实、术语/编号查询、表格用例查询、代码查询、跨文档汇总、多轮追问和无法回答的问题。
- 为每类准备代表性样本及期望来源，明确系统覆盖范围、拒答边界、权限要求、延迟与成本目标。
- 先建立小型人工核对的基线，再扩展评测集；不要先定模型和框架后再寻找使用场景。

阶段二：资料采集与版本管理
- 设计资料清单：来源系统、资源 ID、标题、类型、权限、更新时间、采集状态、内容哈希。
- 采集过程支持分页、断点续跑、失败清单和非零退出；开始新一轮采集时先标记“未完成”，全部校验成功后才标记“完成”，避免旧成功记录掩盖半批新数据。
- 区分“目录/索引文档”和“它链接的正文”：若目录自身含知识，也必须入库。
- 对限时签名的附件或图片，先下载、校验并落地，再解析；说明失效链接如何刷新。
- 不得因为个别资源无权限就假装全量采集成功。

阶段三：按资料类型解析与清洗
- 文档：保留标题层级、段落、列表、代码围栏、表格、链接及来源信息。先修复导出格式造成的标题层级或代码围栏错误，再分块。
- 表格：保留列名、行主键、单条记录的完整字段；测试用例等自包含行可以直接作为检索和回答单元，不必机械套用父子块。
- 代码：保留仓库、路径、文件、符号和必要上下文；区分代码本身与生成的代码说明。
- 图片/PDF：判断其中是否含答案所需的图表、报文、数字；用代表性样本比较 OCR、版面解析和多模态解析的准确率、显存及耗时。解析结果与原图位置、来源绑定。
- 清洗时分别处理图片链接、文本链接和裸 URL；任何正则改动都用样本验证，避免把有效链接清成空链接。

阶段四：分块与标识
- 根据资料结构选择语义边界，而不是所有资料统一按字符数切割。
- 对长文档可采用“子块召回、父块提供回答上下文”：子块保留标题路径和精确术语，父块保留完整语义。
- 不要为了减少碎片，把独立术语、命令或用例编号强行并入相邻长段落；但被排版拆开的“字段标签—字段值”应恢复为同一语义单元。
- 设计稳定的来源 ID、块 ID 和数据版本。新增图片块等内容时避免无谓改变正文块 ID；源文档重排后必须检测评测锚点是否失效，不能仅靠 ID 相同就认定语义相同。
- 输出分块质量检查：空块、重复块、超大块、孤儿标签、缺失父块及来源丢失。

阶段五：索引与检索
- 先建立关键词检索和向量检索基线；若问题同时包含精确编号与语义表达，再比较混合检索。
- 可采用 BM25 + 向量召回、RRF 融合、交叉编码器精排、去重/多样性控制、父块扩展的链路；每一步都通过同一评测集证明增益。
- 依据数据量、更新频率、并发和运维能力，比较本地 FAISS/文件索引与专用向量数据库；不要因“架构先进”而引入不必要服务。
- 用真实问题调节召回数量、精排池、阈值等参数，并记录延迟、显存和检索质量。
- 对共享 GPU 设计资源隔离：明确模型放在哪张卡、批大小、并发限制及构建与线上问答的互斥规则；不占用或终止其他人的进程。

阶段六：问答生成与可信性
- 检索证据优先于历史对话；多轮问题可以改写，但不得凭空补充用户未提供的事实。改写失败时退回原问题。
- 生成答案只依据当前可访问的证据，并给出可核查来源；证据不足时明确说明，不能编造。
- 将检索到的资料视为不可信输入，隔离其中的指令，防止提示词注入和越权引用。
- 如使用推理模型，实测网关对思考模式、输出 token、温度和结构化输出参数的支持；不要仅凭模型名称或文档推断参数生效。

阶段七：评测与迭代
- 分开评测采集完整性、解析准确性、检索命中、排序质量、答案正确性、证据支撑、拒答和延迟。
- 评测题的正确来源应在出题时锚定，不能事后靠关键词搜索反推。每条题记录数据版本、来源和标注依据。
- 同时准备真实检索上下文与困难负例；不能只用“保证正确资料已给出”的理想上下文证明线上质量。
- 每次调整先做离线回归和 A/B，再决定发布或回滚。明确“块 ID 命中率不等于答案正确率”；锚点失效时停止报告全量质量分数。
- 列出哪些测试无需模型 API（解析、索引结构、检索、备份恢复等），哪些必须获得授权后才能调用 API（生成回答、模型裁判等）。

阶段八：Web、权限与部署
- 设计问答页面、来源展示、会话管理和必要的管理入口；明确系统是内部共享、单租户还是多租户，不可把内部共享服务直接当作公网产品。
- 本地开发、远端运行时，使用明确的代码同步清单和逐文件校验；代码同步不得覆盖远端原始资料、索引、模型、会话和环境文件。
- API Key、SSH 凭据及管理令牌通过环境变量或密钥管理注入，不写入源码、示例配置、日志或同步包；限制环境文件权限。
- 服务要有实际进程核对、就绪检查、异常重启、日志轮转和权限保护。说明就绪检查能证明什么、不能证明什么。

阶段九：索引发布、备份与恢复
- 新索引在独立候选目录构建；检查采集是否完成、分块关系、文件校验和、模型标识及离线回归后，再原子切换线上版本。
- 保留上一版本并演练回滚；构建失败不得影响当前在线索引。
- 区分原始资料、清洗资料、分块、索引、用户修订、会话数据库、代码和密钥各自的备份策略。
- 备份后验证哈希及数据库一致性，并定期恢复到独立新目录；异机副本与服务器本机备份分别记录。
- 删除旧 backup 目录之前，先确认内容、恢复依赖和替代快照；不能仅凭目录名判断为无效残留。

最终请交付：
A. 系统架构图与端到端数据流；
B. 分阶段实施清单，每项标注“必需/条件触发/暂不做”；
C. 技术选型对比及选择条件；
D. 关键目录、数据结构、接口和版本规则；
E. 每阶段的验收用例及通过门槛；
F. 已知风险、失败处理、回滚与恢复操作；
G. 需要我确认的少量关键决策。

实施时一次只推进一个可验收阶段。每阶段结束报告：完成内容、验证证据、未验证部分、下一阶段前置条件。不要把“代码已写好”当成“系统已可用”。
